# 5.0 release-candidate readiness

The local candidate is `inline-css@5.0.0-rc.1` with nine independently versioned companion packages. No push, merge, npm publication or stable promotion has been performed.

## Checks

- The regression baseline initially recorded 22 failures and one passing control. Dependency security and Node compatibility are exercised through actual audits/installs rather than manifest-text unit tests.
- Existing fixture tests now compare DOM attributes/text and browser-computed CSS values, preserving rendering expectations while allowing declaration order/fallback changes. Snapshot fixtures were not regenerated from implementation output. New explicit browser tests cover shorthand, important, fallback, quotes, variables, and functional specificity.
- Resource tests use local servers for redirects, decoded bytes/compression, exact boundaries, total budgets, queues, cancellation, DNS results, direct-only proxy behavior, and credential isolation. No live GitHub/Yahoo requests remain in the test suite.
- `npm ci --ignore-scripts` succeeded on Node 22.12.0, and `npm ls` resolved the workspace tree without invalid dependencies.
- Both full-tree and production audits reported zero advisories after patched transitive tool dependencies were installed. The glob/minimatch overrides require the updated test-tool APIs; coverage was executed to verify that compatibility.
- The complete `release:check` command runs lint, the full suite including browser checks, audits and packed consumers. Final verification passed 162 tests; counts and results are recorded in the execution ledger.
- Packed-consumer verification creates all ten npm tarballs, checks their entries/licenses/file boundaries, then resolves actual semver dependency ranges through a temporary local registry with no overrides or pre-existing consumer lockfile. Standalone entry points and root conversion examples are exercised without workspace symlinks.
- Focused runtime regressions pass on Node 24 and 26. A clean consumer rejects Node 22.11.0 under npm's strict engine checking. The exact Node 22.12.0 floor is used for full checks.
- Linux/Windows CI is configured for Node 22.12.0, current 22, 24 and 26, but remote CI has not run because the branch has not been pushed. Local checks do not establish Windows CI success.
- The independent review's URL resolution, nth-selector skipping and root publication findings have targeted regressions. Changesets forbids custom `--tag` during prerelease mode: the publisher honors its `rc` tag for companions, then separately publishes the root under `next`. A command-boundary test intercepts npm instead of publishing; preview is side-effect-free.
- Lint has zero errors. Remaining warnings are explained validation/orchestration complexity, one nested conditional, and the public four-argument callback/loader contracts exceeding the existing three-parameter warning threshold. No lint rules were disabled globally to hide them.

## Candidate publication, after authorization

1. Review the branch and run remote CI after an authorized push/PR.
2. Run `npm run release:check` from a clean checkout and inspect `npm run release:preview`.
3. Confirm ownership/availability of new npm package names before first publication.
4. Only after explicit publication authorization, run `npm run release`. The command checks first, publishes companion packages using Changesets prerelease state (`rc`), and publishes root `inline-css` under `next`.
5. Verify a clean registry install of `inline-css@next` and resolved companion versions. Only a real authorized publication can establish registry success.

## Stable promotion remains gated

Obtain representative production profiles/RC feedback, including slow/high-count workloads and proxy-dependent applications. The current illustrative public corpus fits the RC limits, but is not statistical production validation. Revisit limits together with tests and docs if needed.

For stable promotion, exit Changesets prerelease mode, apply the reviewed workspace version plan, explicitly set root `inline-css` to `5.0.0` and update its internal dependency ranges, regenerate the lockfile/changelogs, and repeat all checks. The current RC-only publish script deliberately rejects stable versions. Stable publication and dist-tag changes require separate authorization; publish dependencies before the root and verify no prerelease ranges remain.
